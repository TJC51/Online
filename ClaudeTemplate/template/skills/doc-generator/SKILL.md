# 功能文档生成器

从代码库中梳理业务逻辑，生成格式化的功能文档（Markdown），输出到 `doc/` 目录。

## 触发条件

用户说类似以下话语时触发：
- "帮我分析XX功能，并输出一份文档"
- "分析XX模块，生成功能文档"
- "为XX生成文档"

**不触发**：用户只说"看下XX功能"、"了解下XX代码"等仅阅读不输出的场景。

## 核心工作流

```
用户触发
    │
    ▼
Step 1: 范围侦察
    ├─ 读取模块 CLAUDE.md、包结构、核心数据表
    ├─ 判断范围大小：
    │   ├─ 小功能（≤3 个主要 Service 类 + ≤2 张核心表）→ 1 个分析单元
    │   └─ 大模块（超出上述范围）→ 拆分为 N 个子功能
    ├─ 大模块时：列出子功能清单，展示给用户确认
    │
    ▼
Step 2: 并行/串行分析
    ├─ 小功能 → 串行，深入分析（按「分析 SOP」执行）
    └─ 大模块 → 并行，每个子功能派一个 Agent 同时分析
    │
    ▼
Step 3: 输出文档
    ├─ 小功能 → doc/<模块>-<功能>.md
    └─ 大模块 → doc/<模块>-<子功能1>.md … + doc/<模块>-总览.md
```

## Step 1: 范围侦察

### 1.1 定位目标

根据用户输入的模块名/功能名，定位到对应的模块目录。搜索顺序：
1. 精确匹配 `{模块名}/CLAUDE.md`
2. 模糊搜索 `*{关键词}*/CLAUDE.md`
3. 列出现有模块 CLAUDE.md 让用户选择

### 1.2 读取模块 CLAUDE.md

读取目标模块的 CLAUDE.md，获取：
- 模块职责、核心服务、关键业务概念
- 子模块结构和依赖关系
- 核心数据表名

### 1.3 判断范围大小

| 判断维度 | 小功能 | 大模块 |
|---------|--------|--------|
| 核心 Service 类数 | ≤ 3 | > 3 |
| 核心数据表数 | ≤ 2 | > 2 |
| 涉及独立子流程 | 否 | 是（多个独立子功能） |

### 1.4 拆分功能列表（大模块时）

大模块按**业务子领域**拆分，不按代码层拆分。拆分原则：
- 每个子功能是一个独立的业务场景（如"费用单管理"、"对账单管理"）
- 子功能之间有清晰边界（不同核心表、不同 Service）
- 拆分粒度对齐参考文档的「子功能」粒度

拆分后展示给用户确认：

```
该模块可拆分为以下子功能：
1. 费用单管理 — bc_expense_order 表，ExpenseOrderService
2. 预付单管理 — bc_pre_payment 表，PrePaymentService
3. 结算项管理 — bc_settlement_item 表，SettlementItemService
...

是否按此拆分继续？如需调整请说明。
```

用户确认后再进入 Step 2。

## Step 2: 分析执行

### 2.1 小功能 — 串行分析

直接按「分析 SOP」执行 7 个步骤，输出一份 6 章文档。

### 2.2 大模块 — 并行分析

为每个子功能创建一个 Agent，并发分析。Agent 统一使用「分析 SOP」作为 Prompt：

```
你是一个功能文档分析师。请对目标子功能执行以下 SOP，最终输出一份完整的 6 章 Markdown 文档。

目标子功能：{子功能名}
所属模块：{模块名}
核心文件：{从 Step 1 收集的关键文件列表}

## 分析 SOP
[嵌入完整 SOP，见下方]

## 输出
将完整的 6 章文档内容作为你的最终回复。不要添加任何解释性文字。
```

启动并行 Agent 示例：
```
parallel(subFeatures.map(f => () =>
  agent(`...SOP...`, {label: `分析:${f.name}`, schema: DOC_SCHEMA})
))
```

所有子 Agent 完成后，收集文档，进入 Step 3。

### 2.3 增量更新

如果目标文件已存在（`doc/<模块>-<功能>.md`）：
1. 读取现有文档，了解已有结构
2. 对比代码变化（主要是 Service/Controller 层的方法变更）
3. 仅更新受影响的章节
4. 在文档顶部更新增量标记：
   ```
   > 📝 更新于 2026-06-13，更新内容：签署回调逻辑变更、新增批量查价接口
   ```

## 分析 SOP（7 步骤）

### S1: 构建文件清单

- 读取模块 CLAUDE.md，找到功能相关的 Controller/Action 类
- 从 Controller 追踪到 Service 接口和实现类
- 定位 Repo/Mapper（MyBatis-Plus 或 XML）
- 定位 PO 类 / 数据表对应的实体
- 定位定时任务（scheduler/job 目录）
- 定位 MQ 消费者/生产者

### S2: 提取 API 清单

- 读取 Controller/Action 类，提取所有 REST 端点
- 记录：路径、HTTP 方法、Action Key、请求/响应参数、用途
- 产出 → 第 6 章「附录」的 API 表格

### S3: 深入分析核心业务逻辑

逐方法阅读核心 Service 实现，重点关注：

**保存/提交：**
- 基础校验（必填字段、数据类型、关联校验）
- 业务规则校验（状态约束、时间重叠、唯一性等）
- 数据转换逻辑（DTO → PO，字段计算）
- 事务边界

**审批流程：**
- 审批通过/拒绝时的状态变更
- 审批通过后的后续操作（如发起签署、发送 MQ）
- 查看审批回调入口（REST 回调接口）

**签署流程：**
- 签署服务的调用（Facade/Gateway 类）
- 签署回调的状态处理
- 签署成功/拒绝/撤回的不同分支

**状态机/生命周期：**
- 找到状态枚举/常量定义
- 追踪所有状态变更点（哪些方法会改状态）
- 梳理合法状态转换路径

**定时任务：**
- 扫描 scheduler/job 目录
- 记录 Job Key、触发端点、扫描条件、处理逻辑

**特殊设计：**
- 冗余字段（如快速查询索引）的设计意图
- 复杂校验链的组织方式
- 有学习价值的代码逻辑

> ⚠️ 重要：S3 的分析必须标注 **代码位置**（`类名.方法名()`），方便读者溯源。

### S4: 提取数据模型

- 读取 PO 类，提取字段名、类型、Javadoc 注释
- 对比数据库表结构（如有 DDL 或 MyBatis XML）
- 提取枚举值（搜索 `enum` 目录或 PO 中的常量字段）
- 梳理表关系（1:N / N:N）
- 识别特殊字段：冗余索引字段、状态字段、版本字段
- 产出 → 第 3 章「模型设计」

### S5: 反推状态机

- 从 S3 的状态变更逻辑 + S4 的枚举值反推状态机
- 确认每个状态的合法前驱和后继
- 如果有签署状态，单独绘制签署状态机
- 产出格式：Mermaid `stateDiagram-v2`
- 产出 → 第 4 章「状态流转」

### S6: 提取定时任务和 MQ

- 定时任务：Job Key、触发端点、执行逻辑摘要
- MQ 消息：消息类型/Key、发送时机、消费逻辑
- 配置项：控制定时任务启用的配置 key
- 产出 → 第 6 章「附录」的定时任务/MQ 表格

### S7: 撰写文档

按 6 章模板撰写最终文档。**写作要求：**
- 遵循 `documentation.md` 规范：h1 仅文件标题，h2 用于章节，代码块指定语言
- 表格列不超过 4 列，保持对齐
- 列表项以空行分隔
- 引用代码位置使用相对路径 + 行号链接：`[文件名](相对路径#L行号)`
- 在文档末尾标注生成信息：`> 本文档由 Claude Code doc-generator 生成于 YYYY-MM-DD`
- 不要放任何"本文档介绍"、"总结"等水话——直接上干货

## Step 3: 输出文档

### 3.1 小功能输出

直接将分析结果写入 `doc/<模块名>-<功能名>.md`。

### 3.2 大模块输出

1. 各子功能文档写入 `doc/<模块名>-<子功能名>.md`
2. 生成总览文档 `doc/<模块名>-总览.md`，结构为 6 章模板的"俯瞰版"：

```markdown
# {模块名} - 总览

## 1. 模块概述
* 整体定位
* 子功能清单及关系（关联到各子功能文档）
* 共享概念/角色

## 2. 整体业务流程
* 模块级的主流程（子功能间的协作）

## 3. 模型总览
* 全部核心数据表清单
* 表间 ER 关系图

## 4. 状态流转总览
* 涉及哪些状态、各状态在各子功能中如何流转

## 5. 代码结构
* 模块目录树 + 各子模块/包职责

## 6. 附录
* 全部 API 汇总
* 全部定时任务汇总
* 全部 MQ 消息汇总
```

生成各子功能文档后，再单开一个 Agent 读取所有子功能文档，从中提取关键信息合成总览。

3. 全部生成完成后，告知用户输出清单。

## 工作原则

- **先零后整**：大模块必须拆成子功能分别分析，不得一上来就试图覆盖全部
- **代码溯源**：所有结论必须标注代码位置（类名.方法名 或 文件路径:行号）
- **用户确认**：大模块拆分方案必须用户确认后才执行
- **增量优先**：已有文档优先增量更新，避免重复工作
- **无则生成**：`doc/` 目录不存在时自动创建
- **遵循规范**：严格遵循 `documentation.md` 中的 Markdown 规范
